1. 打开网站，用自己的话描述它的用途。

   我理解这个网站是在帮 Demo Buyer 处理 DEMO-SKU-A 的供应关系。这里有供应商 A 和供应商 B。供应商 A 的模拟基础价格是每单位 12.00 美元，不包括续约增价。供应商 B 的基础价格是每单位 12.60 美元。

   页面里有三种方案。D0 是继续保留 A。D1 是保留 A 的最低采购份额，同时引入 B。D2 是退出 A，把采购转到 B。这个页面不是只比较单价，也不是直接告诉用户选哪一个。它还会看财务风险、服务能不能连续、以及合同方面可能出现的下行风险。

   我觉得它更像一个供应商决策分析工具。它先把合同里的内容找出来，再变成模型参数。之后把这些参数放到不同的情景里，比较 D0、D1、D2。刚打开时，我以为它会直接给出推荐方案。往下看了一会儿，才发现它更在意“这个结果是怎么来的”。

2. 打开合同原文，说明证据与参数的关系。

   Data Intake 页面有四份输入资料：历史需求、供应商交付记录、期初库存和 Supplier A agreement.pdf。合同是机器可读的 PDF，一共 6 页。页面里有一条证据 EV-014，指向合同第 4 页。

   EV-014 的内容是，如果没有提前至少 60 天发出书面通知，合同会自动续约。页面没有停在“60 天”这个数字上，又把它转成了几个后续计算会用到的参数：通知窗口 60 天、供应商 A 的最低采购比例 60%、续约溢价 14%。

   我的理解是，合同原文属于证据。60 天、60% 和 14% 属于从证据里提取出来的业务参数。后面的方案比较会用到这些参数。页面里还出现了 renewal locked-in 和 minimum share A。第一次看时有点绕，仔细看后能理解它们都和合同续约、最低采购义务有关，只是说的是两个不同方面。

3. 打开 Scenario Lab，区分假设和 D0/D1/D2。

   Scenario Lab 里有 Baseline、Demand −15%、Cash stress 和 Lead-time stress。这些是外部情景，意思是外部环境可能发生变化。页面还给了三个可以调整的值：Demand shock、Stockout risk cap 和 Cash ceiling。它们属于当前情景下的假设或约束。

   D0、D1、D2 是另外一类东西。D0 是继续全部使用供应商 A。D1 是保留 A 的最低份额，再引入 B。D2 是退出 A，转到 B。我的理解是，情景代表“外面发生什么”，方案代表“我们可以怎么做”。

   这里有一个容易看错的地方。滑块改了以后，页面上的假设会变，但这不等于模拟已经重新算完。页面也写了，修改的只是 draft，需要重新请求模拟才会有新的结果。刚开始我会下意识地把变化后的数字当成结果，看到提示后才改过来。

4. 运行模拟，比较方案；记录成功、失败和耗时。

   这次重新测试时，页面先显示服务正在唤醒。等了一会儿，健康检查变成了 **Simulation service reachable · ready**。之后进入 Decision Matrix，点击 Run simulation，Baseline 模拟成功返回。

   这次返回的是 1,000 次 Monte Carlo runs，seed 是 1042026。Baseline 的结果是：D0 为 365,811 美元，缺货概率 92%，P90 为 369,631 美元；D1 为 348,040 美元，缺货概率 1%，P90 为 348,723 美元；D2 为 356,665 美元，缺货概率 90%，P90 为 361,811 美元。系统选中了 D1。

   这次和之前不一样，矩阵上出现了 **LIVE API · 104 WEEKS**，页面也显示 Validated POST /api/simulate response。页面还给出了新的 request ID：`req-53ca59a970664da4a54245f4e5b1b4bb`。保存示例仍然在页面里，但已经和实时结果区分开了。

   从点击 Run simulation 到结果返回，大约用了 15 秒。结果：实时模拟成功，返回并通过了页面的校验。原来“实时模拟失败”的记录只适用于第一次测试，这次需要改成成功。

5. 打开 Formula Trace，解释 TCO、缺货概率、服务水平和 P90。

   Formula Trace 展示的是 D1 的一组结果。TCO 是 24 个月的预期总成本，D1 是 348,040 美元。页面把它拆成了采购成本、持有成本、缺货损失、续约溢价和终止费用。

   缺货概率是 1%。它表示模拟中出现缺货的概率。服务水平是 100.0%，可以理解为需求被满足的比例。P90 是 348,723 美元。页面把它放在 cash outflow 下面，我的理解是，它表示现金流出比较高的一档，不是普通平均值。

   公式里还列了更细的数字：采购成本 318,240 美元，持有成本 3,590 美元，缺货损失 2 美元，续约溢价 26,208 美元，终止费用 0 美元，加起来是 348,040 美元。

   TCO、缺货概率和服务水平比较好理解。P90 需要多看一会儿。只看 P90 这个名字，不太容易知道它和平均成本的差别。看到 cash outflow 和 90 分位的说明后，才知道它是在看现金压力较大的情况。

6. 检查同一运行的合同证据与 PDF 高亮。

   Verified Golden 页面里有 EV-014、EV-019、EV-020 和 EV-024。这些证据都和同一个 simulation ID 绑定。EV-014 指向 Supplier A agreement.pdf 第 4 页的 60 天条款。

   这能看出当前运行用到的参数不是凭空来的，可以追溯回合同里的具体内容。证据编号、合同页码和 simulation ID 放在一起，关系比较清楚。只是如果用户只看结果数字，不点开证据，不一定会主动发现这条关系。

7. 打开 AI Boardroom，记录当前未配置状态与模拟结果是否保留。

   重新运行模拟后，进入 AI Boardroom，页面没有直接把旧的缓存评审套过来，而是显示当前实时模拟已经有结果，但匹配的 Boardroom 还在等待。页面提供了“Run Boardroom for Demand −15%”按钮，并说明需要针对当前 simulation ID、dataVersion 和场景单独请求 Boardroom。

   之前缓存里的 D0、D1、D2、simulation ID、数据版本、合同证据和 Critic 意见仍然可以查看。新的 Demand −15% 模拟结果也保留了，但页面没有把旧 Boardroom 的三个视角直接显示到新运行下面。这样看，模拟结果和 Boardroom 评审是分开的。

   这里仍然会有一点疑惑。页面一方面显示实时模拟已经成功，另一方面又显示 Boardroom waiting。看完说明后能分清：模拟已经完成，但 AI Boardroom 还没有针对这次运行完成评审。

8. 改动假设并重新运行，确认旧评审不会成为新运行的评审。

   这次把情景改成了 **Demand −15%**，页面显示需求下降，但供应商 A 的最低采购承诺仍然保留。回到 Decision Matrix 后，点击 Run simulation，新的结果成功返回。

   新的 Demand −15% 结果是：D0 为 310,547 美元，缺货概率 26%，P90 为 316,020 美元；D1 为 358,161 美元，缺货概率 0%，P90 为 358,829 美元；D2 为 306,401 美元，缺货概率 96%，P90 为 312,919 美元。页面选中了 D1。

   这次返回了新的 request ID：`req-3778f68ad0c3461f83f94028dd255b02`，场景也变成了 `demand-drop`。进入 AI Boardroom 后，页面没有直接显示之前的评审，而是显示 **WAITING FOR MATCHING BOARDROOM**，并提供“Run Boardroom for Demand −15%”按钮。页面还写明 Boardroom 必须绑定当前 simulation ID、dataVersion 和当前场景。

   这说明旧的 Baseline 评审没有直接套到 Demand −15% 上。新的模拟结果已经保留，但新的 Boardroom 评审还没有运行。

9. 打开 Verified cache，说明它与实时计算的区别。

   Verified cache 是网站里保存好的完整快照。它已经经过复核，是只读的。打开时不会发 API 请求，也不会重新调用 AI。页面里还能看到 1,000 次运行、seed、dataset、simulation ID 和证据链。

   实时计算不一样。它需要 simulation service 真正响应，还要通过数据结构、矩阵、成本合计、Decision Delta 和约束条件等检查，新的结果才会被接受。

   简单说，缓存适合查看一条已经固定下来的完整记录。实时计算用来验证新假设。这次两种状态都看到了：Baseline 和 Demand −15% 都返回了实时矩阵，Verified cache 仍然是单独的只读快照。

10. 用窄屏检查导航、阅读与按钮。

   这次用手机打开了网站，截图时手机屏幕是竖屏。页面能正常加载，顶部的 LOCAL MOCK · TRACEABLE、Open saved example 和 Simulation service reachable · ready 都能看到。健康状态卡片会自动换行，文字没有压到按钮上，Recheck health 按钮也还可以单独点击。

   页面导航改成了横向排列。Data Intake、Scenario Lab、Decision Matrix 能看到，右侧的 AI Boardroom 只露出一部分，需要横向滑动才能继续看。这一点不算功能坏了，但第一次用时不太明显，可能会让人以为后面的导航不见了。

   中间的 Proof Engine 卡片在手机上会变成长卡片，标题和说明文字都能正常换行，没有出现文字盖住文字的情况。Evidence、Variable、Matrix 三个小标签也能看到，按钮大小基本够点。页面内容比较长，往下读需要一直滚动，暂时没有发现横向滚动条把整页撑开。

   这次主要检查了页面加载、横向导航、卡片阅读和按钮显示。Scenario Lab 里的滑块、Formula Trace 弹窗和 Decision Matrix 的完整表格还需要再单独点一遍。当前手机截图已经确认首页窄屏布局可以正常显示，但横向导航需要更明显的滑动提示。

   结果：手机竖屏测试通过页面加载和基本阅读；横向导航可以使用，但右侧项目被截断，需要滑动；长页面和部分交互还需要继续点测。

反馈对应的修复位置、优先级与原因：

1. Data Intake / Scenario Lab 顶部：实时服务没有准备好时，用户不容易判断自己是否真的完成了模拟。建议把“实时运行失败”“查看保存示例”和“打开缓存快照”分开显示。优先级：P1。

3. Formula Trace：P90 对第一次使用的人不够直观。可以在旁边加一句中文解释，比如“较高压力情况下的现金流出水平”。优先级：P2。

4. 全站：英文术语比较多。可以保留英文，但在旁边加简短中文解释。优先级：P2。
